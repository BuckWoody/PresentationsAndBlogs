Two ways to answer the same question

What happens when a reader shows up while a writer is still working, told through SQL Server's locks and PostgreSQL's row versions.

Every relational database eventually has to settle an uncomfortable question: what happens when one transaction is changing a row while another transaction wants to look at it. SQL Server and PostgreSQL settle that question in almost opposite ways, and the difference is behind a lot of the blocking chains and phantom slowdowns that show up in production without an obvious cause.

Below are two small animated schematics that walk through the same scenario, a withdrawal against an account balance, once under SQL Server's default locking behavior and once under PostgreSQL's MVCC. Watch what happens to the reader in each version, that is the part that actually matters.

SQL Server: pessimistic locking

SQL Server's default isolation level, read committed, protects a row under modification with an exclusive lock held for the life of the write transaction. Any reader that wants the same row has to request a shared lock first, and the lock manager will not hand one out while an incompatible exclusive lock is outstanding. The reader waits, full stop.

-- Transaction A (writer)
BEGIN TRAN;
UPDATE accounts SET balance = 400 WHERE account_id = 42;
-- exclusive lock held here, transaction still open

-- Transaction B (reader), starts while A is still open
SELECT balance FROM accounts WHERE account_id = 42;
-- blocks until A commits or rolls back

Animation paused for reduced motion. Transaction A takes an exclusive lock while updating the row. Transaction B requests the same row and waits, because a shared lock cannot be granted while the exclusive lock is outstanding. Once A commits, the lock releases and B reads the new value.

Transaction A opens an update against account 42 and takes an exclusive lock on the row. Transaction B asks for the same row a moment later and requests a shared lock, which the lock manager cannot grant while the exclusive lock is outstanding, so B sits and waits. Once A commits, the exclusive lock releases, B's shared lock is granted immediately, and B reads the new balance of 400. Had A rolled back instead, B would have read 500 and never known a change was attempted.

SQL Server can trade this behavior for something closer to MVCC by turning on read committed snapshot isolation or full snapshot isolation, both of which keep row versions in tempdb. Plenty of shops never touch that switch, so the locking behavior above is still what most SQL Server workloads run into by default.

PostgreSQL: multiversion concurrency control

PostgreSQL never blocks a reader on a writer. Every row carries hidden bookkeeping columns, xmin and xmax, recording which transaction created it and which transaction, if any, has superseded it. An update does not touch the existing row at all, it writes an entirely new tuple version and marks the old one as superseded. A reader's snapshot decides which version it sees, and that decision gets made once, when the reader's transaction starts.

-- Transaction A (writer)
BEGIN;
UPDATE accounts SET balance = 400 WHERE account_id = 42;
-- new tuple written, xmin = 101, not yet committed

-- Transaction B (reader), snapshot taken before A commits
SELECT balance FROM accounts WHERE account_id = 42;
-- returns 500 immediately, no wait at all

Animation paused for reduced motion. Transaction A writes a new tuple version without touching the old one. Transaction B's snapshot was taken before A committed, so B reads the old tuple immediately, with no wait. After commit, the new tuple becomes current and the old one becomes dead weight until vacuum removes it.

Transaction A's update writes a new tuple version, balance 400, tagged with its own transaction id, and marks the old tuple's xmax with that same id. Transaction B's snapshot was taken before A committed, so the old tuple is still valid as far as B is concerned, and B reads 500 without any wait at all. Once A commits, the new tuple becomes the current version for any transaction whose snapshot starts afterward. The old tuple becomes dead weight, still sitting in the table file until a vacuum process reclaims it.

Postgres is not immune to blocking, two writers touching the same row will still fight over it. It is specifically reader-versus-writer contention that MVCC sidesteps.

Same row, two philosophies

Line them up side by side and the design philosophies come into focus. SQL Server keeps one copy of the row and controls access with locks, cheap to check, expensive to wait on. PostgreSQL keeps multiple copies of the row and controls access with time, cheap to read, expensive to store until vacuum catches up. Neither approach is free, you are choosing between blocking readers and bloating tables, and which one costs you more depends entirely on your workload.

Pick your poison. Just know which one you picked.
