PostgreSQL Configuration: Where Settings Live and Which One Wins

SQL Server spreads its settings across the master database, the Windows registry, Configuration Manager, startup parameters, and trace flags. PostgreSQL keeps nearly all of it in a few text files and a couple of catalogs. This page lines the two up, shows how the layers stack, walks through server startup, and lets you test pg_hba.conf rules yourself.

Two files, two jobs

pg_hba.conf answers one question: who is allowed to connect, from where, and how do they prove who they are? It is not the main configuration file, and nothing you run in SQL can write to it or override it. You edit it as text and reload.

Server settings such as memory, logging, and the port live in postgresql.conf. When you run ALTER SYSTEM in SQL, the change is written to a second file, postgresql.auto.conf. The server reads that file after postgresql.conf, so it wins when both set the same parameter. That second-file-wins behavior is the one that overrides things.

2. Which setting wins when the same parameter is set in several places

A single parameter such as work_mem can be set in many layers at once. The server keeps the value from the highest layer that sets it. Tick the boxes below to decide which layers have a value, and watch the winner change. Each layer carries an example value so you can see which one the server picks.

Seeing the winner on a real server

The source column of pg_settings tells you which layer supplied the current value. sourcefile and sourceline point to the exact line.

SELECT name, setting, unit, source,
       sourcefile, sourceline, pending_restart
FROM pg_settings
WHERE name = 'work_mem';

To see every file line and which ones lost, query pg_file_settings. A row with applied false was read but overridden.

SELECT sourcefile, sourceline, name, setting, applied, error
FROM pg_file_settings
WHERE name = 'work_mem';

Some parameters can only live near the bottom

Every parameter has a context that decides how far up the stack it may go. shared_buffers has the context postmaster. Only the files and the command line can set it, and only at startup. SET shared_buffers or ALTER ROLE ... SET shared_buffers is rejected with a message that it cannot be changed without restarting the server.

The context table in section 6 lists the four you will meet most often.

Changing things while the server runs: reload versus restart

A reload makes the server re-read postgresql.conf, postgresql.auto.conf, pg_hba.conf, and pg_ident.conf without stopping. Any of these starts one:

SELECT pg_reload_conf();
pg_ctl reload -D "path to the data directory"

On Linux packages the service manager has its own reload command, such as systemctl reload. On Windows, pg_ctl reload or the SQL function are the usual routes.

  • A reload disconnects nobody. New pg_hba.conf rules apply to new connections only.
  • A reload is forgiving. If one value is bad, the server logs the problem and keeps the old value for that parameter. If the file has a syntax error, the whole file is rejected. At startup, by contrast, either problem stops the server from starting.
  • If pg_hba.conf is broken at reload time, the server keeps the previous rules in memory and writes the error to the log.
  • Parameters with the context postmaster are only read at startup. Changing them in a file does nothing until the next restart, and pending_restart in pg_settings will show true.

4. Try it: which pg_hba.conf line applies to a connection?

When a client connects, the server reads pg_hba.conf from the top and stops at the first line that matches the connection type, database, user, and address. It does not keep looking if that line's method then fails. If no line matches, the connection is refused. Pick a connection and see which line catches it. The five lines below are an example file, so the line numbers here are simpler than a real file with comments and blank lines.

LineTYPEDATABASEUSERADDRESSMETHODResult for this connection

On Windows there is normally no Unix socket, so connections arrive as host lines. The socket choice is included here because most Linux packages ship with local lines.

A real file can do more than this example shows. A record can continue onto the next line if the line ends with a backslash. Since PostgreSQL 16 the database and user fields also accept regular expressions (written with a leading slash), and include, include_if_exists, and include_dir lines can pull in other files. The matching rule stays the same: top to bottom, first match wins.

5. Other control mechanisms

Besides the two main files and ALTER SYSTEM, PostgreSQL has several other places where a setting can come from. Open each one for the detail.

A map turns the name that the operating system or a certificate gives you into a database role name. A pg_hba.conf line opts in with map=mapname. It is read at startup and on reload, exactly like pg_hba.conf.

# pg_ident.conf
# MAPNAME    SYSTEM-USERNAME     DATABASE-USERNAME
ops          deploy              app_user

# pg_hba.conf
local   all   app_user   peer   map=ops

These store a default value in the pg_db_role_setting catalog. The server applies them after authentication succeeds, so they affect new sessions only. A role-in-database default beats a role default, which beats a database default. ALTER ROLE ALL SET stores a default for every role in every database. It sits below the database defaults and above the command line. This is the closest thing PostgreSQL has to per-login option defaults in SQL Server.

ALTER DATABASE pubs SET work_mem = '48MB';
ALTER ROLE report_user SET work_mem = '64MB';
ALTER ROLE report_user IN DATABASE pubs SET statement_timeout = '30s';

Because they live in a catalog and not in a file, they travel with a physical backup and with pg_dumpall. A copy of the config files alone will not include them.

SET lasts until the session ends or you run RESET. SET LOCAL lasts until the end of the current transaction. Both sit at the top of the stack. Only parameters whose context is user, or superuser for a superuser, can be changed this way.

SET work_mem = '200MB';
BEGIN;
SET LOCAL work_mem = '300MB';
COMMIT;
SELECT set_config('app.current_store_id', '7066', false);

Custom names with a dot, such as app.current_store_id above, are allowed for your own variables. A row-level security policy can read one with current_setting('app.current_store_id'). Extensions use the same pattern, as in pg_stat_statements.track.

Anything passed with -c beats both config files. This is the nearest thing to SQL Server startup parameters, and it is set in the service definition or the systemd unit.

postgres -D "path to the data directory" -c log_connections=on
postgres -C shared_buffers -D "path to the data directory"

The second command prints the value the server would use without starting it. That is a handy check when a server will not start.

postgresql.conf can pull in other files. The included content is read at the point of the directive, and the last assignment for a parameter wins. Configuration management tools often drop one small file per concern into an included directory so nothing edits the main file.

include_dir = 'conf.d'
include_if_exists = 'local-overrides.conf'

Section Config File Includes in the default file shows where these go. pg_file_settings reports the real file for each line.

These do not configure the server. They control how a client such as psql connects. PGHOST, PGPORT, PGDATABASE, PGUSER, and PGSSLMODE fill in missing connection details. PGOPTIONS can send server parameters at connect time, and those arrive above the role and database defaults. Saved passwords go in a pgpass file, and named connections go in pg_service.conf. The nearest SQL Server ideas are connection strings and saved SSMS connections.

PGDATA is the one that matters to the server tools. It points pg_ctl and postgres at the data directory when you do not pass -D.

  • Server parameters are changed in the portal (Settings, Server parameters) or with the Azure CLI. The page shows whether a parameter needs a restart.
  • The job of pg_hba.conf is covered by the server firewall rules and the networking settings.
  • Parameters the provider controls are read-only, and the administrator login is not a true superuser.

6. Editing it correctly

Three kinds of change, three habits.

Change a server setting

Run ALTER SYSTEM as its own statement. It cannot run inside a transaction block.

ALTER SYSTEM SET work_mem = '32MB';
SELECT pg_reload_conf();

SELECT name, setting, source, pending_restart
FROM pg_settings
WHERE name = 'work_mem';

ALTER SYSTEM RESET work_mem;
  • Use RESET to remove a value you added. Do not hand-edit postgresql.auto.conf.
  • For settings you want in version control, edit postgresql.conf or an included file instead, and keep ALTER SYSTEM for quick changes.
  • PostgreSQL 17 and later: allow_alter_system = off makes ALTER SYSTEM return an error. Teams that manage config with an external tool use it to stop well-meaning edits. It is a guardrail, not a security control. Superusers can still reach the file by other routes, and values already in postgresql.auto.conf still apply.

Change who can connect

  1. Find the file with SHOW hba_file; and keep a copy.
  2. Edit it. Put specific lines above general ones, because the first match wins.
  3. Check the file before you load it. This view reads the file on disk, and needs superuser rights by default.
SELECT line_number, type, database,
       user_name, address, auth_method, error
FROM pg_hba_file_rules;
  1. Reload with SELECT pg_reload_conf();
  2. Open a new session to test it while your existing session is still open.

Change it for one database, role, or session

ALTER DATABASE pubs
  SET work_mem = '48MB';

ALTER ROLE report_user
  SET work_mem = '64MB';

SET work_mem = '200MB';

BEGIN;
SET LOCAL work_mem = '300MB';
COMMIT;

The ALTER forms apply to new connections. The two SET forms apply to the current session or transaction only.
