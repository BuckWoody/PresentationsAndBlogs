Windows Active Directory Users in PostgreSQL: Setup Steps and the Login Flow

In SQL Server, one statement turns a Windows account into a login. PostgreSQL splits that job in two: a role says who exists and what they may do, and a pg_hba.conf line says how they prove who they are. This page shows the setup steps for each approach, then follows a login from the first packet to the first query.

Active Directory proves identity. It does not create users.

PostgreSQL never reads your directory to build a user list. Every person who needs access gets a role created in PostgreSQL, and the authentication method on the matching pg_hba.conf line hands the password check, or the Kerberos check, to Active Directory.

AD groups are not imported either. There is no equivalent of CREATE LOGIN [CONTOSO\DBAs] FROM WINDOWS. Section 5 covers the options for groups.

What you do in SQL Server, and what it takes in PostgreSQL

SQL Server PostgreSQL Notes
CREATE LOGIN [CONTOSO\jsmith] FROM WINDOWS CREATE ROLE jsmith LOGIN; plus a pg_hba.conf line that uses sspi, gss, or ldap Two pieces, in two places. The role has no password.
CREATE LOGIN [CONTOSO\DBAs] FROM WINDOWS for a group No direct equivalent. A group role (NOLOGIN) holds permissions and each person is added to it. Membership is managed in PostgreSQL, by hand or by a sync tool.
CREATE USER ... FOR LOGIN in each database Not needed. Roles are cluster-wide. Grant CONNECT and object privileges. Every role can connect to a database unless you revoke CONNECT from PUBLIC.
Server roles such as sysadmin Role attributes (SUPERUSER, CREATEDB) and predefined roles such as pg_read_all_data (PostgreSQL 14 and later) Hand out the smallest set that works.
SPN MSSQLSvc/host:1433 registered with setspn SPN postgres/host.fqdn registered with setspn, or a keytab file for GSSAPI Same idea, different service name.
auth_scheme in sys.dm_exec_connections The log_connections entry: connection authenticated: identity=... method=... PostgreSQL 14 and later. It also names the pg_hba.conf line that matched.
ALTER LOGIN ... DISABLE ALTER ROLE jsmith NOLOGIN; Disabling the AD account alone does not remove the role.

1. Choose how PostgreSQL will check the identity

Three methods cover on-premises Active Directory. The right one usually follows from where PostgreSQL runs and whether users can sign in with a domain account.

Method (pg_hba.conf METHOD)Single sign-onWhere the server runsDoes a password reach PostgreSQL?Choose it when
sspi
SQL Server cousin: Windows Authentication		 Yes. Kerberos first, then NTLM if Kerberos is not possible. Windows, joined to the domain No PostgreSQL runs on Windows and users sign in with domain accounts. This is the closest match to what SQL Server pros expect.
gss
SQL Server cousin: Windows Authentication on Linux		 Yes, Kerberos only Any operating system. Needs a keytab file. No PostgreSQL runs on Linux, or you want Kerberos only with no NTLM fallback.
ldap
No direct cousin		 No. The user types an AD password. Any operating system Yes, in clear text inside the client connection. Use TLS. Clients are not domain-joined, or an application needs to ask for AD credentials.
Microsoft Entra ID Yes, through Entra tokens Azure Database for PostgreSQL No. A token is used as the password. You use the managed service. On-premises AD accounts must be synced to Entra ID first.

For all three on-premises methods, the matching role must already exist in PostgreSQL. The authentication method only decides whether the person is who they say they are.

2. The setup steps, per method

Each step is tagged with who normally does it. Pick the tab that matches your method. The role and permission steps are the same for all three, and the permission part is in section 5.

AD admin DBA User

Step 1. Register the service principal nameAD admin

Kerberos needs to know which account runs PostgreSQL. Register an SPN on that account, using the server's fully qualified name. If the service runs as Network Service (check in services.msc), the account is the server's computer account.

:: service runs as a domain account
setspn -S postgres/dbhost.contoso.com CONTOSO\svc_postgres

:: service runs as Network Service: use the computer account
setspn -S postgres/dbhost.contoso.com DBHOST

:: confirm
setspn -L DBHOST

Skipping this step does not break the login. SSPI quietly falls back to NTLM, which is the weaker path. Do not skip it.

The PostgreSQL docs note that Active Directory expects the service name in upper case (POSTGRES), while libpq defaults to lower case (postgres). Pick one spelling for the SPN and set krbsrvname to match on clients that need it. Test with one client first.

Step 2. Create the roleDBA
CREATE ROLE jsmith LOGIN;

No password. Active Directory proves identity, and PostgreSQL only needs the role to exist. The role name is the name the person will connect as.

Without a map (Step 3), the role name has to match exactly what SSPI hands over, which by default is jsmith@CONTOSO. That works with CREATE ROLE "jsmith@CONTOSO" LOGIN;, but every user then needs -U with that quoted name. A short role name plus a map is easier to live with.

Step 3. Add a map in pg_ident.confDBA
# MAPNAME    SYSTEM-USERNAME      DATABASE-USERNAME
ad_users     /^(.*)@CONTOSO$      \1

SSPI gives PostgreSQL an identity of the form user@NETBIOSDOMAIN, because compat_realm defaults to 1. The regular expression keeps the part before the @ and only accepts the CONTOSO domain. A same-named account from another trusted domain does not match.

The PostgreSQL docs recommend keeping include_realm at its default and using a map, instead of stripping the realm.

Step 4. Add the pg_hba.conf lineDBA
# TYPE    DATABASE  USER  ADDRESS       METHOD
hostssl   all       all   10.0.0.0/8    sspi map=ad_users

The first matching line wins, so place this above any scram-sha-256 catch-all. If it sits below one, users will be asked for a password and never see single sign-on. Kerberos sends no password, but hostssl still protects the data that follows.

Step 5. Check, then reloadDBA
SELECT line_number, type, user_name, auth_method, options, error
FROM pg_hba_file_rules;

SELECT * FROM pg_ident_file_mappings;   -- PostgreSQL 15 and later

SELECT pg_reload_conf();

Both views read the files on disk, so you can catch a typo before the reload. A bad line shows a message in the error column.

Step 6. ConnectUser
psql -h dbhost.contoso.com -U jsmith -d pubs

The user is signed in to Windows as CONTOSO\jsmith and sees no password prompt. Use the server's full name, the same one used in the SPN. An IP address or an alias gives Kerberos nothing to build the service name from, and Negotiate falls back to NTLM.

With log_connections on, the server log shows a line like connection authenticated: identity="jsmith@CONTOSO" method=sspi, followed by the pg_hba.conf path and line number (PostgreSQL 14 and later). Write your map against exactly that identity value.

Step 1. Create a service account and export a keytabAD admin

A Linux server cannot use a computer account the way a Windows server can. Create a service account, give it the SPN, and export a keytab file with the key that the server will use to open tickets.

:: run once on a domain controller or admin workstation
ktpass -princ postgres/dbhost.contoso.com@CONTOSO.COM -mapuser CONTOSO\svc_postgres -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -pass * -out postgres.keytab

The realm is written in upper case. ktpass resets the service account password and bumps the key version, so run it once and keep the keytab safe. Re-running it invalidates the previous file.

Step 2. Install the keytab on the serverDBA
# postgresql.conf
krb_server_keyfile = '/etc/postgresql/postgres.keytab'

Make the file readable only by the operating system account that runs PostgreSQL. The docs recommend a separate keytab just for PostgreSQL, not the system-wide one. Reload to pick up the setting.

Step 3. Create the role and the mapDBA
CREATE ROLE jsmith LOGIN;

# pg_ident.conf
# MAPNAME    SYSTEM-USERNAME          DATABASE-USERNAME
ad_users     /^(.*)@CONTOSO\.COM$     \1

GSSAPI hands over the full Kerberos principal, jsmith@CONTOSO.COM, with the realm in upper case. The map turns it into the short role name and only accepts the CONTOSO.COM realm.

Step 4. Add the pg_hba.conf lineDBA
# TYPE    DATABASE  USER  ADDRESS       METHOD
hostssl   all       all   10.0.0.0/8    gss map=ad_users

Kerberos does not encrypt the session on its own. Use hostssl for TLS, or hostgssenc to have GSSAPI encrypt the connection itself.

Step 5. Check, then reloadDBA
SELECT line_number, type, user_name, auth_method, options, error
FROM pg_hba_file_rules;

SELECT pg_reload_conf();
Step 6. ConnectUser
# Windows client: psql uses the signed-in domain account automatically
psql -h dbhost.contoso.com -U jsmith -d pubs

# Linux client: get a ticket first
kinit jsmith@CONTOSO.COM
psql -h dbhost.contoso.com -U jsmith -d pubs

As with SSPI, use the full host name that matches the SPN. If the server asks for the service name in upper case, add krbsrvname=POSTGRES to the connection string.

Step 1. Prepare Active Directory for the lookupsAD admin
  • Make sure the domain controllers answer on LDAPS (port 636), or allow StartTLS. The PostgreSQL server must trust the certificate that the controllers present.
  • For the simple bind style below, nothing else is needed.
  • For the search+bind style, create a read-only service account that can search the directory.
Step 2. Create the roleDBA
CREATE ROLE jsmith LOGIN;

Per the PostgreSQL docs, the user must already exist in the database before LDAP can be used. The role name is the name the person types when connecting. There is no map for LDAP, so that name is also what is sent to AD.

Step 3. Add the pg_hba.conf lineDBA

Simple bind. PostgreSQL builds the sign-in name from a prefix, the role name, and a suffix, then binds to AD as that user.

# TYPE    DATABASE  USER  ADDRESS      METHOD
hostssl   all       all   10.0.0.0/8   ldap ldapserver=dc1.contoso.com ldapscheme=ldaps ldapsuffix="@contoso.com"

The suffix form builds a user principal name such as jsmith@contoso.com. In Active Directory you can also use ldapprefix with the NetBIOS style DOMAIN\.

Search+bind. PostgreSQL first binds with a service account, finds the user's entry, then binds again as that user with the password the client gave.

hostssl   all       all   10.0.0.0/8   ldap ldapserver=dc1.contoso.com ldapscheme=ldaps
          ldapbasedn="DC=contoso,DC=com"
          ldapbinddn="CN=svc_pgldap,OU=Service Accounts,DC=contoso,DC=com"
          ldapbindpasswd="the service account password"
          ldapsearchattribute=sAMAccountName

In a real file this is one long line, because pg_hba.conf records cannot be continued. The bind password sits in the file in clear text, so lock down who can read it. ldapsearchfilter lets you require membership in an AD group before a login is accepted. Check the PostgreSQL docs for the filter syntax.

Step 4. Check, then reloadDBA
SELECT line_number, type, user_name, auth_method, options, error
FROM pg_hba_file_rules;

SELECT pg_reload_conf();
Step 5. ConnectUser
psql "host=dbhost.contoso.com dbname=pubs user=jsmith sslmode=require"

The user is prompted for a password and types the AD password.

The password reaches PostgreSQL in clear text, and that is why hostssl and sslmode=require matter here. Setting ldapscheme or ldaptls only protects the leg between PostgreSQL and the domain controller. Failed attempts count against the AD account lockout policy.

The order matters. The server picks the pg_hba.conf line before anything is proven, and only checks that the role exists after the identity is proven. That is why a wrong name gives a vague "authentication failed" and not "role does not exist". The error tells an outsider nothing about which names are real.

5. After the login works: permissions, groups, and off-boarding

Give permissions through group roles

CREATE ROLE pubs_readers NOLOGIN;
GRANT pg_read_all_data TO pubs_readers;
GRANT pubs_readers TO jsmith;

Permissions go to the group role, and people are added to it. pg_read_all_data is a predefined role in PostgreSQL 14 and later. On older versions, grant SELECT on the tables or schema instead.

Remove access when someone leaves

ALTER ROLE jsmith NOLOGIN;

SELECT pg_terminate_backend(pid)
FROM pg_stat_activity
WHERE usename = 'jsmith';

Disabling the AD account stops new tickets and password checks, but a Kerberos ticket already issued stays valid until it expires, and open sessions keep running. The role also stays. Change it to NOLOGIN, end sessions, and drop it once nothing depends on it.

What about AD groups?

PostgreSQL cannot see AD group membership during login. You have three realistic options.

  • Manage membership in PostgreSQL. Add each person to the right group role when they are created. Simple, and easy to audit. Often fine for small teams.
  • Sync on a schedule. A community tool such as pg-ldap-sync reads AD groups and creates matching roles and memberships in PostgreSQL.
  • Gate the login with a group (LDAP only). With search+bind, ldapsearchfilter can require membership in an AD group. That decides who may log in, while privileges still come from PostgreSQL roles.

6. Troubleshooting guide

What you seeLikely causeWhere to look
no pg_hba.conf entry for host ... No line matches the address, database, role, or SSL setting. pg_hba_file_rules, and the connection type (host or hostssl).
Password prompt when you expected single sign-on An earlier line, often scram-sha-256, matched first. Line order in pg_hba.conf. The first match wins.
SSPI authentication failed for user "jsmith" or the GSSAPI version The identity from AD, after include_realm and the map, does not equal the requested role. Also appears when a map line is missing or the client omitted -U. The identity= value in the log_connections line, and the name builder above.
role "jsmith" does not exist Authentication worked. The role was never created. CREATE ROLE jsmith LOGIN;
role "jsmith" is not permitted to log in The role exists without the LOGIN attribute, or was set to NOLOGIN. ALTER ROLE jsmith LOGIN; if intended.
Works on some PCs but not others, or silently uses NTLM Connected by IP address or an alias, so no SPN matches. Or the SPN is missing, duplicated, or on the wrong account. Or the PC is not on the domain. klist on the client, setspn -L and setspn -X for duplicates.
Kerberos fails after it worked yesterday Clock difference of more than a few minutes between client, server, and domain controller, or a changed service account password or key. Time sync on all three, and whether the keytab was regenerated.
LDAP authentication failed for user "jsmith" Wrong password, a locked-out account, a bad prefix or suffix, or the server cannot reach or trust the domain controller. The PostgreSQL server log, which carries the LDAP library's reason, and AD lockout status.
