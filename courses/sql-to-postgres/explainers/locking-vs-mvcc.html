SQL Server Locking vs PostgreSQL MVCC: Who Waits for Whom

Every database must decide what happens when one transaction is changing a row while another wants to read it. SQL Server answers with locks, and PostgreSQL answers with row versions. This page puts the two side by side, steps through one scenario in each engine, and covers the places where the usual advice breaks down.

The short version

SQL Server, by default, keeps one copy of a row and uses locks. A reader waits for a writer, and a writer can wait for a reader. PostgreSQL keeps more than one copy of a row. A reader looks at the version that was current when its snapshot was taken, so it does not wait for a writer, and a writer does not wait for a reader.

Neither is free. SQL Server pays with waiting. PostgreSQL pays with dead row versions that vacuum has to clean up. Two writers on the same row wait for each other in both engines, and a few kinds of statement, such as most ALTER TABLE forms, still block readers in PostgreSQL.

1. Side by side

The left column describes SQL Server with its default settings. SQL Server can also keep row versions, which is covered in the stepper in section 2, so read the left column as "SQL Server without row versioning" unless it says otherwise.

Question SQL Server (default) PostgreSQL
What does a plain SELECT take? Shared locks on the rows it reads, plus intent locks above them. Under READ COMMITTED each shared lock is released as soon as the row is read. No row locks. A table-level ACCESS SHARE lock that conflicts only with ACCESS EXCLUSIVE.
What does an UPDATE do to the row? Takes an exclusive lock on the row and changes it in place. The old value is kept in the transaction log so the change can be undone. Writes a whole new row version and marks the old one as replaced. Nothing is edited in place.
Does a reader wait for a writer? Yes, unless row versioning is turned on (READ_COMMITTED_SNAPSHOT or snapshot isolation). No.
Does a writer wait for a reader? Yes, for as long as the reader holds a shared lock. That is only an instant under READ COMMITTED, but until the transaction ends under REPEATABLE READ and SERIALIZABLE. No.
Two writers, same row? The second waits for the first one's exclusive lock, then continues with the new value. The second waits for the first transaction to finish. Under READ COMMITTED it then continues with the new value. Under REPEATABLE READ or SERIALIZABLE it fails with SQLSTATE 40001 and must be retried.
Where do old versions live? Nowhere, by default. With row versioning on, in the version store: in tempdb, or in the user database when accelerated database recovery (ADR) is on. In the table itself, next to the live row, until vacuum removes them.
What cleans up? Nothing to clean for plain updates. With row versioning, a background task removes versions nobody needs. VACUUM, run for you by autovacuum, which is on by default.
Lock memory and escalation Locks live in memory. A statement that takes about 5,000 or more locks on one table or index can trigger escalation to a table lock. No escalation. Row locks are marks in the row header, so there is no limit on how many rows can be locked. Table-level locks do sit in a shared memory pool.
Deadlocks Detected. One session is the victim and gets error 1205. Detected after deadlock_timeout (1 second by default). One session gets ERROR: deadlock detected, SQLSTATE 40P01.
What does ROLLBACK cost? The changes are undone from the log, so a big rollback can take as long as the work did. Almost nothing. The new row versions are simply never visible and vacuum removes them later.
What about the newer SQL Server features? Row versioning is on by default in Azure SQL Database. Optimized locking (always on in Azure SQL, opt-in per database in SQL Server 2025) holds one transaction ID lock instead of many row locks, which cuts lock memory and escalation. Nothing to enable. MVCC is the only model.

3. Isolation levels in each engine

The same level names mean different mechanics in each engine. This table is the one to keep open when a SQL Server habit meets a PostgreSQL server.

LevelSQL ServerPostgreSQL
READ UNCOMMITTED Reads rows another transaction has changed but not committed. This is what NOLOCK gives you. Accepted, but it runs as READ COMMITTED. PostgreSQL never shows uncommitted data.
READ COMMITTED The default. With locking, a reader waits for writers. With READ_COMMITTED_SNAPSHOT on, each statement reads the committed data as of its own start, with no waiting. The default. Each statement sees the data committed before that statement began. Two statements in one transaction can see different data.
REPEATABLE READ Holds shared locks until the transaction ends, so writers wait, and phantom rows can still appear. One snapshot for the whole transaction, taken at its first statement. No waiting for writers and no phantom rows. An update to a row that changed after the snapshot fails with 40001.
SNAPSHOT One snapshot per transaction using row versions. It must be enabled with ALLOW_SNAPSHOT_ISOLATION, and a conflicting update fails with error 3960. There is no separate level. REPEATABLE READ is snapshot isolation.
SERIALIZABLE Key-range locks. Readers and writers block each other, and deadlocks are common when transactions read before they write. Serializable snapshot isolation. Nothing blocks, but a transaction can be cancelled with 40001 when the engine spots a pattern that could not be serialized, so it must be retried.

Set a level in PostgreSQL with BEGIN ISOLATION LEVEL REPEATABLE READ; or SET TRANSACTION ISOLATION LEVEL ... as the first statement of the transaction. The server default comes from default_transaction_isolation.

The pattern that loses updates in both engines

The risk is not in the engine. It is in code that reads a value, computes in the application, and writes a literal back.

-- Both sessions run this under READ COMMITTED
SELECT balance FROM accounts WHERE account_id = 42;   -- both read 500
-- the application computes 500 - 100 = 400
UPDATE accounts SET balance = 400 WHERE account_id = 42;  -- B overwrites A: one withdrawal is lost

Three ways out:

  • Do the arithmetic in the statement: SET balance = balance - 100. This is safe under READ COMMITTED in both engines.
  • Lock the row first. In PostgreSQL that is SELECT ... FOR UPDATE. In SQL Server it is SELECT ... WITH (UPDLOCK, ROWLOCK).
  • Use a stricter level and retry on failure (40001 in PostgreSQL, error 3960 or 1205 in SQL Server).

5. Where PostgreSQL readers still wait

"Readers never block" is true for row data and false for a handful of statements. These are the exceptions that cause the surprising outages.

DROP TABLE, TRUNCATE, REINDEX, CLUSTER, VACUUM FULL, a plain REFRESH MATERIALIZED VIEW, and many forms of ALTER TABLE take an ACCESS EXCLUSIVE lock. That is the one table lock that conflicts with the ACCESS SHARE lock every SELECT takes.

The worse part is the queue. If an ALTER TABLE waits behind one long transaction, every new query on that table queues behind the ALTER, so a quick change can stall the whole table. The fix is to refuse to wait:

SET lock_timeout = '3s';
ALTER TABLE accounts ADD COLUMN note text;   -- fails fast if it cannot get the lock, then retry

SQL Server has the same shape with schema modification locks (Sch-M) against schema stability locks (Sch-S), and offers WAIT_AT_LOW_PRIORITY for some online operations. In PostgreSQL, CREATE INDEX CONCURRENTLY and REINDEX ... CONCURRENTLY avoid the blocking lock.

A row lock never blocks a plain SELECT. It blocks writers and other lockers of the same row. FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE, and FOR KEY SHARE differ in how strong they are. Foreign key checks use FOR KEY SHARE, the weakest.

-- take the next job, skip rows another worker already holds
SELECT job_id FROM jobs
WHERE status = 'new'
ORDER BY job_id
LIMIT 1
FOR UPDATE SKIP LOCKED;

SELECT * FROM accounts WHERE account_id = 42 FOR UPDATE NOWAIT;  -- error instead of waiting

The SQL Server cousins are the UPDLOCK, ROWLOCK, and READPAST hints. One PostgreSQL oddity: locking a row writes to the row header, so a large SELECT ... FOR UPDATE can cause disk writes.

When a writer meets another transaction's uncommitted change to the same row, it waits for that transaction to finish. There is no timeout unless you set one. If two transactions end up waiting for each other, the server notices after deadlock_timeout and cancels one of them.

  • Update rows in a consistent order, so two transactions never wait on each other in a circle.
  • Set lock_timeout for work that should give up. It is the counterpart of SET LOCK_TIMEOUT in SQL Server.
  • Turn on log_lock_waits to have the server log any wait longer than deadlock_timeout, which is a cheap way to find chronic blocking.
  • Retry on SQLSTATE 40P01, the way you would retry error 1205.

Advisory locks are locks on a number that the application chooses. The server does not tie them to any table or row. They are the nearest thing to sp_getapplock.

SELECT pg_advisory_lock(42);          -- held until released or the session ends
SELECT pg_advisory_xact_lock(42);     -- released at the end of the transaction
SELECT pg_try_advisory_lock(42);      -- returns false instead of waiting

Session-level advisory locks ignore transactions. A lock taken inside a transaction that rolls back is still held. Use the xact forms unless you need the lock to outlive the transaction.

A session that ran BEGIN, did some work, and then went quiet keeps its locks and keeps its snapshot. Its locks can block other writers and DDL. Its snapshot stops vacuum from removing recent dead rows (section 6). It shows up as idle in transaction in pg_stat_activity. Application code that opens a transaction and then calls a slow web service is the usual cause.

-- cancel sessions that sit idle inside a transaction for more than a minute
ALTER SYSTEM SET idle_in_transaction_session_timeout = '60s';
SELECT pg_reload_conf();

SQL Server has the same problem, since an open transaction holds locks and pins the log. In PostgreSQL it also pins the cleanup of dead rows.

SQL Server may trade thousands of row locks for one table lock, which can suddenly block everyone else on that table. PostgreSQL never does that, because row locks cost no lock memory. The trade is that the row header is written to, and a very large number of locked rows means a lot of writes. Table-level locks and advisory locks do live in a shared memory pool sized by max_locks_per_transaction and max_connections, which is a limit you can hit if one transaction touches thousands of tables or partitions.

6. The bill for MVCC: dead row versions and vacuum

Every update in PostgreSQL leaves the old row version behind, and a delete leaves the deleted one. Once no transaction can still need it, the version is dead. VACUUM finds dead versions and marks their space as reusable. Autovacuum runs it for you, and it is on by default.

Try it: why one open transaction stops cleanup

One account row. Each update leaves the old version behind. Vacuum can only remove a dead version that no open snapshot can still see.

What to know about the bill

  • Table bloat. If dead versions arrive faster than vacuum removes them, tables and indexes grow. A plain VACUUM reuses the space but does not usually return it to the operating system. VACUUM FULL does, by rewriting the table, and it needs an ACCESS EXCLUSIVE lock and extra disk space while it runs.
  • Old transactions. A long-running transaction, an idle-in-transaction session, or a stalled replication slot holds back the cleanup horizon for the whole database. SQL Server shows the same effect with a long snapshot transaction and a growing version store.
  • Write cost. An update writes a complete new row version, and index entries can need updating too. Heap-only tuple (HOT) updates avoid the index work when no indexed column changes and the new version fits on the same page.
  • Transaction ID wraparound. Transaction IDs are 32 bits. Vacuum marks old rows as frozen so they stay visible after the counter wraps. A table must be vacuumed in time, and autovacuum forces an aggressive vacuum when it is not. If a database gets too close to wraparound, PostgreSQL refuses to assign new transaction IDs.
-- which tables carry the most dead rows?
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;

-- how far is each database from wraparound?
SELECT datname, age(datfrozenxid) FROM pg_database;

FROM pg_stat_activity

ORDER BY xact_start

8. Habits that change when you move

Drop the NOLOCK reflex

Plain reads do not wait for writers in PostgreSQL, and they only ever see committed data. There is nothing to work around, and no hint to add.

Keep transactions short, and never idle

Long transactions hurt more here, because they hold back vacuum for everyone. Commit before calling slow services, and set idle_in_transaction_session_timeout.

Build in retries

Anything above READ COMMITTED can raise 40001, and any level can raise 40P01. Retry the whole transaction, not just the statement.

Treat DDL as the blocking exception

Set lock_timeout before schema changes, prefer the CONCURRENTLY forms for indexes, and run changes when no long transaction is open.

Watch autovacuum, not only locks

Add dead rows, vacuum lag, and the age of the oldest transaction to your monitoring, next to the blocking checks you already have.

Know your SQL Server baseline

If your SQL Server databases already run with READ_COMMITTED_SNAPSHOT, you already live with row versions. If they do not, expect the blocking you are used to to disappear, and the cleanup chores to arrive.
